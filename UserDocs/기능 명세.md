# 논문 서지 관리 앱 기능 명세 v0.1

Oct 19, 2026 · @qazcde

## 개요

이 앱은 **노트를 중심에 둔 논문 관리 도구**로, Zotero의 수집·정리·인용 기능은 필요한 만큼만 가져오고 논문 그래프와 AI 에이전트로 차별화한다.

- **저장소**: 구글 계정 로그인 하나로 PDF는 사용자 드라이브에, 메타데이터·노트·하이라이트는 가벼운 백엔드 DB(Firebase 검토)에 둔다.
- **탐색 방식**: 탭 대신 컬렉션을 그래프로 보여주고, 핀 꽂은 논문이 탭 역할을 한다. 실제로 읽는 논문은 하나다.
- **검색 방식**: 원문 전문 검색 대신, AI가 만든 요약·키워드 문서와 사용자 노트를 검색 대상으로 삼는다.
- **AI**: Python LangGraph 에이전트가 uv tool로 등록된 도구를 호출한다. 배포 환경은 클라우드 LLM(Gemini, ChatGPT, Claude), dev 환경은 로컬 llama server도 쓸 수 있다.
- **범위 밖**: 플러그인 확장, 리더 디자인 테마(다크 모드는 지원), 브라우저 커넥터, 수십 종의 인용 스타일.

## 기능 명세

아래 7개 영역이 v1 범위다. 각 항목 끝의 태그는 Zotero 대비 처리 방식이다: \[유지\] \[개선\] \[신규\] \[제거\].

### 1. 자료 수집

1. **사이트별 논문 검색** \[신규\] — 앱 안에서 검색 사이트를 골라 검색하고 결과를 바로 라이브러리에 추가한다.
   1. 검색 사이트: arXiv, OpenReview, DBLP(탑티어 학회 목록), ACL Anthology, CVF Open Access, Semantic Scholar, OpenAlex.
   2. 각 검색 사이트는 에이전트 도구(uv tool)로도 등록되어 AI도 같은 검색을 할 수 있다.
   3. 학회 필터: NeurIPS, ICML, ICLR, CVPR, ACL 등 사용자가 지정한 학회·저널 목록으로 범위를 좁힌다.
2. **파일 업로드** \[유지\] — PDF를 끌어다 놓으면 DOI·arXiv ID·제목을 추출해 메타데이터를 채운다.
3. **식별자로 추가** \[유지\] — DOI, arXiv ID, OpenReview URL 입력.
4. **버전 자동 묶음** \[신규\] — 같은 논문의 arXiv v1/v2, 워크숍 버전, 학회 최종본, 저널 확장본을 자동으로 감지해 하나의 논문 아래 버전으로 묶는다.
   1. 기본 버전(논문을 열면 기본으로 열리는 버전)을 사용자가 지정한다.
   2. 노트와 하이라이트는 버전별로 붙되, 논문 단위로 모아 볼 수 있다.
   3. 새 버전이 나오면 알림(예: arXiv v3 공개, 학회 채택).

### 2. 라이브러리 정리

1. **분류 기준별 컬렉션** \[개선\] — 컬렉션을 여러 "분류 기준"으로 나눈다. 한 논문은 분류 기준마다 다른 컬렉션에 동시에 속한다.
   1. 직접 만드는 분류 기준: 프로젝트, 연구 계보.
   2. 자동 분류 기준(메타데이터에서 생성): 연도, 저자, 학회·저널.
   3. 분류 기준끼리 교차해 필터링(예: 프로젝트 A × 2024년 이후).
2. **논문 그래프** \[개선\] — 연결 기준을 사용자가 바꿔 같은 논문들로 여러 그래프를 만드는 것이 핵심이다.
   1. 인용·피인용 관계는 Semantic Scholar/OpenAlex에서 자동 수집하고, 주기적으로 자동 업데이트한다.
   2. 연결 기준 후보: 인용, 공동 저자, 같은 학회·저널, 같은 노트에 연결됨, 사용자가 정한 관계(확장, 반박, 재현 등).
   3. 연결 기준과 필터 조합을 "저장한 그래프"로 남겨 다시 연다.
3. **중복 탐지·병합** \[유지\] — 버전 묶음(1-4)과 같은 매칭 엔진을 쓰되, 진짜 중복(같은 파일 두 번)은 병합, 다른 버전은 같은 논문의 버전으로 묶는다.
4. **태그** \[유지\] — 분류 기준과 별개인 가벼운 라벨.

### 3. 읽기와 하이라이트

1. **내장 리더** \[유지\] — v1은 PDF. 렌더러를 포맷별 어댑터로 분리해 Markdown을 나중에 붙인다.
2. **링크로 잇는 하이라이트** \[개선\] — 하이라이트는 "표시한 곳 → 연결 대상" 링크가 될 수 있다.
   1. 표시한 곳: 텍스트, 영역(그림·표), 페이지, 논문 전체.
   2. 연결 대상: 다른 논문의 하이라이트, 다른 논문, 노트, 노트의 특정 문단, 외부 URL.
   3. 링크는 양방향으로 조회된다(백링크).
3. **그래프로 이동** \[신규, 탭 대체\] — 컬렉션을 그래프로 띄운다.
   1. 논문에 핀을 꽂으면 제목 또는 별칭이 보인다. 핀을 해제하면 이름 없는 점으로 돌아간다.
   2. 핀 꽂은 논문들이 탭 역할을 한다(핀 꽂기 = 탭 열기, 핀 해제 = 탭 닫기). 리더에서 실제로 열리는 논문은 한 번에 하나이며, 핀 꽂은 다른 논문을 누르면 전환된다.
4. **다크 모드** \[축소\] — 디자인 테마는 두지 않고 라이트/다크만 지원한다.
5. **원문 전문 검색** \[제거\] — 대신 "노트 검색"을 둔다: AI 요약, 핵심 키워드, 사용자 노트, 하이라이트 메모만 검색한다.

### 4. 노트 (핵심 기능)

노트가 제품의 중심이다. Markdown 노트를 위키 링크로 엮고, 노트 그래프를 논문 그래프와 따로 본다.

1. **형식** — Markdown. 리더의 Markdown 어댑터와 렌더러를 공유한다.
2. **위키 링크** — 노트 간 링크(예: `[[노트 제목]]`)와 백링크. 논문·하이라이트로의 링크도 같은 문법 계열로 쓴다(문법은 설계 시 확정).
3. **노트–논문 다대다** — 한 노트가 여러 논문에, 한 논문이 여러 노트에 연결된다. 여러 논문을 엮는 주제 노트가 자연스럽게 가능하다.
4. **노트 그래프** — 노트를 점, 위키 링크를 선으로 그린 별도 그래프. 연결된 논문을 함께 표시하는 옵션을 둔다.
5. **템플릿** — 사용자가 노트 템플릿을 만들고 편집·삭제한다. 기본 예시(리뷰 노트, 실험 노트)를 제공한다.
6. **AI 노트** — AI가 만든 요약·키워드도 노트로 저장되어 편집·링크·검색할 수 있다.
7. **검색** — 노트는 노트 검색의 1순위 대상이다.

### 5. 인용 및 참고문헌

1. **주요 인용 스타일** \[축소\] — APA, IEEE, ACM, Chicago 정도와 BibTeX 내보내기.
2. **빠른 복사** \[유지\] — 선택한 논문을 지정 스타일 또는 인용 키(BibTeX)로 즉시 클립보드에 복사.
3. 워드프로세서 플러그인 \[제거\]

### 6. 동기화 및 저장소

- **로그인** \[개선\] — 구글 계정 하나로 앱 인증과 드라이브 권한(`drive.file`)을 함께 받는다.
- **PDF 파일** — 사용자 구글 드라이브의 앱 폴더에 저장한다.
- **메타데이터·노트·하이라이트·링크·저장한 그래프** — 가벼운 백엔드 DB에 저장한다. Firebase(Firestore) 무료 플랜을 1순위로 검토하고, 무료 한도는 설계 시 확인한다.
- 기기 간 동기화와 충돌 처리는 DB의 실시간 동기화에 맡긴다.

### 7. AI 기능

- **기능**: 요약(논문 전체·섹션·선택 영역), 하이라이트 제안, 논문 Q&A, 여러 논문 비교 Q&A, 관계 제안, 사이트별 검색 대행.
- **LLM 선택**: 사용자가 모델을 고른다.
  - 배포 환경(웹): 클라우드 LLM만 — Gemini, ChatGPT(OpenAI), Claude.
  - dev(로컬 실행): 위 세 가지 + 로컬 llama server(OpenAI 호환 엔드포인트). llama server 옵션은 dev에서만 노출된다.
- **API 키**: 사용자가 자기 키를 입력한다(BYOK). 키는 암호화해 저장하며, 앱은 LLM 비용을 부담하지 않는다. 가입은 구글 계정으로만 한다.
- **구조**: 오케스트레이션은 Python LangGraph, 에이전트 도구는 uv tool 패키지로 만들어 등록한다.

### 범위 밖

- 브라우저 커넥터 \[보류, 당장 불필요\]

## 기술 설계 메모

배포 환경은 웹 앱 + 클라우드 백엔드 서버로 돌고, dev 환경만 로컬 llama server를 쓴다. 가장 큰 설계 결정은 하이라이트·링크 데이터 모델이다.

실행 환경은 두 가지다. 배포 환경은 백엔드 서버가 클라우드에 있고 클라우드 LLM만 호출한다. dev는 웹 앱과 백엔드 서버를 모두 로컬에서 띄우므로 같은 PC의 llama server에 접근할 수 있다.

### 저장소: 드라이브 + Firebase

- **드라이브 권한 범위**: `drive.file` 스코프를 권장한다. 앱이 만든 파일에만 접근하므로 구글의 민감 스코프 심사 부담이 작다. 드라이브 전체 접근(`drive`)은 제한 스코프라 외부 보안 심사가 필요하다.
- **드라이브는 PDF만**: `/논문앱/files/<논문ID>/<버전ID>.pdf`. 파일 ID를 DB에 기록한다.
- **Firebase**: 구글 로그인(Firebase Authentication)과 Firestore를 함께 쓰면 인증 한 번으로 DB와 드라이브 권한을 처리할 수 있다. 오프라인 캐시와 기기 간 동기화도 Firestore가 맡는다.
- **API 키 보관**: 키는 백엔드 서버에서 암호화해 Firestore에 암호문으로 저장하고, 암호화 키는 서버 쪽 비밀 관리(예: Google Cloud KMS 또는 Secret Manager)에 둔다. 평문 키는 브라우저로 다시 내려보내지 않고 마지막 4자리만 표시한다. Firestore 보안 규칙으로 본인 문서만 접근하게 한다.
- 드라이브에 SQLite 파일을 두는 방식은 쓰지 않으므로 동시 쓰기 충돌 위험이 사라진다.

### 버전 매칭

- 1차: 식별자 일치 — arXiv ID(버전 접미사 제거), DOI, OpenReview forum ID, Semantic Scholar paper ID.
- 2차: 정규화 제목 유사도 + 제1저자 성 + 연도 ±2년.
- Semantic Scholar/OpenAlex가 한 논문의 arXiv ID와 DOI를 함께 주는 경우가 많아 2차 매칭의 근거로 쓴다.
- 같은 파일 해시면 "중복", 다른 파일이면 같은 논문의 "버전"으로 분기한다.

### 하이라이트·링크 데이터 모델

- W3C Web Annotation 데이터 모델의 선택자(selector) 개념을 따르면 포맷에 상관없이 하이라이트 위치를 나타낼 수 있다: 텍스트 인용 선택자는 PDF와 Markdown 모두에 쓰이고, PDF 영역은 페이지+좌표 선택자로 표현한다.
- 링크는 별도 엔티티: `{id, from: 하이라이트 위치, to: 하이라이트 위치|논문|노트, type, created_by: user|agent}`. 백링크와 논문 그래프가 모두 이 테이블에서 나온다.

### 리더와 그래프

- PDF 렌더링은 pdf.js가 표준 선택지다.
- 그래프는 Cytoscape.js(관계별 스타일, 레이아웃 다양) 또는 Sigma.js(점 수천 개 이상 성능)를 검토한다.

### 노트 검색

- 인덱스 대상: AI 요약, 키워드, 노트, 하이라이트 메모.
- 키워드 검색(SQLite FTS5)과 임베딩 검색을 함께 쓰는 하이브리드 방식. 인덱스는 로컬에서 재생성 가능하므로 동기화 대상에서 뺄 수 있다.

### LangGraph + uv tool

- 각 도구 = 독립 Python 패키지 + CLI 진입점. `uv tool install`로 설치하면 도구마다 격리된 가상환경을 가져 의존성 충돌이 없다.
- 도구 계약: JSON 입력(stdin) → JSON 출력(stdout), `--schema`로 입력 스키마 출력. 레지스트리 파일이 도구 목록을 갖고, LangGraph가 각 도구를 서브프로세스 호출 래퍼로 감싸 등록한다.
- 대안: 각 uv tool을 MCP 서버로 만들어 `uvx`로 실행하고 LangChain MCP 어댑터로 붙이면 표준 프로토콜을 그대로 쓸 수 있다.
- **LLM 라우팅**: 공급자별 LangChain 채팅 모델(Gemini, OpenAI, Anthropic)을 하나의 선택 계층 뒤에 둔다. llama server는 OpenAI 호환이므로 OpenAI 모델에 base URL만 바꿔 붙인다. 환경 플래그(예: `APP_ENV=dev`)일 때만 llama server 옵션을 목록에 노출한다.
- 초기 도구 후보: `arxiv-search`, `openreview-search`, `dblp-venue-search`, `s2-citations`, `pdf-extract`, `version-match`, `note-search`.

## 미결 사항

9개 모두 답변을 받아 본문에 반영했다. 현재 남은 미결 사항은 없다.

- [x] **플랫폼**: 웹 앱, 데스크톱 앱(Tauri/Electron), 또는 둘 다? LangGraph 에이전트가 서버에서 도는지 로컬 Python 사이드카로 도는지가 여기서 갈린다. => 웹앱
- [x] **메타데이터 저장 위치**: 드라이브만 쓰는 변경 로그 방식인가, 별도 백엔드 DB를 두는가? => 아주 가벼운 백엔드 DB를 사용한다. =>  firebase 등 무료 db 검토
- [x] **노트 기능 상세**: 노트가 핵심인 만큼 정의가 필요하다 — 형식(Markdown/블록 에디터), 노트 간 위키 링크, 노트 템플릿(리뷰 노트, 실험 노트), 노트를 그래프의 노드로 보이게 할지, 여러 논문을 엮는 "주제 노트". => 노트 형식: markdown, 노트 간 위키 링크 필요, 노트 템플릿도 사용자가 관리할 수 있게 함, 노트 그래프는 별도로 볼 수 있다. 그래프가 핵심이다, 노트와 논문은 다대다 매핑 가능.
- [x] **연구 계보의 정의**: 인용 관계 자동 수집 위주인가, 사용자가 큐레이션하는 계보 위주인가? 계보 축 컬렉션과 그래프의 관계는? => 인용관계 자동수집, 자동 업데이트, 그래프의 엣지 특성에 따라 다양한 그래프 생성 가능. 즉 엣지 기준을 사용자가 변경 가능하다는 것이 핵심.
- [x] **그래프 내비게이션 범위**: 여러 논문을 동시에 "활성"으로 열 때 리더 화면은 분할인가, 하나만 열리는가? 탭이 없을 때 최근 연 논문으로 돌아가는 방법은? => 활성은 탭의 역할이고, 실제 읽는 논문은 하나다.
- [x] **LLM 공급자**: 사용자 API 키 입력 방식인가, 앱이 제공하는가? 로컬 모델 지원 여부. => 둘다 지원. 즉 cloud llm(gemini, chatgpt, claude 셋다 지원) 및 local llm(llama server) 지원해야함. 사실상 llama server는 openai compatible 이므로 둘다 지원 가능. 즉 로컬에서 띄우면 local llm 사용할 수 있어야 하고 llm을 선택할 수 있는 기능이 필요.
- [x] **다크 모드**: 디자인 테마는 빼되 다크 모드 하나는 둘지. => 다크 모드 지원
- [x] **브라우저 커넥터**: 소스별 검색으로 충분한지, 아니면 웹에서 보던 논문을 바로 저장하는 확장도 필요한지. => 이건 당장은 필요 없음.

* [x] **클라우드 LLM API 키**: 사용자가 자기 키를 입력하는가, 앱이 키를 제공하고 사용량을 관리하는가? 앱이 제공하면 비용과 사용량 제한 정책이 필요하다. => 회원가입은 구글 계정으로 하고 사용자에게 llm API 키를 받으면 암호화해서 저장.
